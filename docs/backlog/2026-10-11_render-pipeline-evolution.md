# Эволюция рендер-пайплайна: worker → прерывание → координатор + рендер-узлы

Это одна линия развития, а не четыре отдельные фичи. Живой рендер при перетаскивании слайдера (stretch 2 спринта 1, перенесён в next-release-features — `docs/planning.md`) требует, чтобы правило «новый запрос вытесняет ждущий» реально работало. Каждый следующий шаг ниже решает это лучше и заодно масштабирует рендер. Делать по порядку и только когда нужно.

## Сервер без worker уже корректен

Модель «на соединение одна задача рендерится, одна ждёт, новая затирает ждущую» правильная, и последний запрос клиента сервер всегда в итоге отрендерит. Клиент отбрасывает ответы на всё, кроме последнего `requestId`. Поэтому что бы клиент ни делал, на экране в итоге картинка для последнего состояния графа. Проблема ниже — про скорость, а не про правильность. При слайдере «рендер на отпускание» (UI заблокирован до ответа, клиент шлёт строго по одному запросу) она не проявляется вовсе.

Правило «1 + 1» действует на соединение, а поток у сервера один: две вкладки рендерятся по очереди, не параллельно.

## Проблема: пачка запросов даёт лишний рендер

Рендер — синхронный JS. Пока он идёт, JS не может обрабатывать входящие сообщения: `#3`, `#4`, `#5` лежат в буфере сокета ОС и не доходят до `pending` в `packages/server/src/ws.ts`. Рендер `#2` закончился → цикл отправляет ответ и видит пустой `pending` (сообщения ещё в буфере) → сервер свободен. Затем Bun раздаёт накопившееся **по одному**. Первым приходит `#3` на свободный сервер и по правилам запускается сразу, сервер снова глохнет, `#4` и `#5` ждут ещё один рендер. В итоге `2, 3, 5` вместо `2, 5`: лишний рендер устаревшего значения (~2 с на ~2 MP), и пользователь сначала видит промежуточную картинку.

Суть: «новый затирает ждущий» работает только для сообщений, уже дошедших до JS, а решение «что дальше» сервер принимает, зная только о первом из накопившихся. Спросить у Bun, сколько ещё лежит в сокете, нельзя. Поэтому паузы — гадание: `await Bun.sleep(0)` после рендера не помогает и ломает `ws.test.ts`. Один `setImmediate` помог в одном прогоне и не помог в другом, `setImmediate` ×3 и `Bun.sleep(50)` сработали по разу. Через прокси vite поведение то же.

Рассматривали и клиентский вариант — не слать следующий запрос, пока не пришёл ответ, держать одно последнее значение. Он детерминированный и дешёвый, но размазывает одну и ту же очередь на две стороны. Выбрали worker.

## Замеры (2026-10-11, 1150×1650, noize 0.5)

| Фаза                           | Время                   |
| ------------------------------ | ----------------------- |
| декодирование jpeg (`canvas`)  | ~30 мс (первый раз ~80) |
| пиксельный цикл lib            | 0.5–0.9 с               |
| **кодирование png (`canvas`)** | **~1.5 с, 4.4 MB**      |
| base64 + JSON                  | ~6 мс                   |

Главный блокирующий кусок — кодирование png, а не пиксельный цикл. Шумная картинка почти не сжимается.

## Шаг 1 — worker без прерывания (сделан 2026-10-11)

Весь рендер (`runGraph` + `encodePng` + base64) идёт в одном worker thread: `packages/server/src/render-worker.ts`, вызов и очередь — `render.ts`. `ws.ts` после валидации zod только отправляет граф в worker и ждёт ответ, `run-graph.ts` / `codec.ts` / `server.ts` не менялись. Основной поток не глохнет, сообщения доходят до `pending` во время рендера, и когда `#2` готов, там уже лежит `#5`. `#2` досчитывается до конца.

- **Один worker на процесс, не пул.** Нативный `canvas` роняет весь процесс Bun (`panic: NAPI FATAL ERROR: Error::New napi_create_error`, Bun 1.3.14), как только его реально использует второй worker — параллельно или после `terminate()` и запуска нового. Одна загрузка lib (barrel тянет `canvas`) в нескольких воркерах не падает, падает использование. `canvas` в основном потоке (декодирование при загрузке) и в одном worker одновременно работают.
- **Рендеры разных соединений идут в worker по очереди** — цепочка промисов в `render.ts`. Для одного соединения больше одного рендера одновременно и так не бывает (очередь `ws.ts`).
- **Упавший worker не перезапускаем** (перезапуск с `canvas` роняет Bun): `onerror` только отклоняет текущий рендер.
- **Первый вариант был переусложнён и выброшен:** пул по числу ядер, параметр `renderWorkers` через весь сервер, разрезание `runGraph` (декодирование в основном потоке, пиксели в worker с передачей буфера). Пиксели без кодирования в worker не помогли: кодирование png ~1.5 с осталось в основном потоке, и в замере было `#2 → #5 → #6 → #9` вместо `#2 → #6 → #9`.
- **Проверено:** тест в `packages/server/tests/server.test.ts` («a burst → the first and the latest are rendered») на старом коде стабильно падает (`7` вместо `8`), с worker — зелёный 5 из 5. Сценарий слайдера на 1150×1650 (сообщения с шагом 150 мс, `#2…#6`, пауза, `#7…#9`) дал ровно `#2 → #6 → #9` в трёх прогонах из трёх.
- **Остаток:** декодирование в worker тоже синхронное, но короткое и уже не в основном потоке. Кэш декодированного исходника — `docs/backlog/2026-10-11_decoded-source-cache.md`.

Шаг 1 за рамками спринта 1: со слайдером «на отпускание» он не нужен. Нужен вместе с живым рендером при перетаскивании.

## Шаг 2 — прерывание (опционально)

Пришёл `#5`, а `#2` ещё считается — не ждём, а прерываем `#2` и сразу запускаем `#5`. При перетаскивании задержка сокращается примерно вдвое. Спека спринта 1 называет это «real abort = worker, later».

- **`worker.terminate()` + новый worker — с `canvas` невозможно:** второй worker, который кодирует png, роняет процесс. Возможно только после замены `canvas` (sharp/libvips — `docs/backlog/2026-08-30_sharp-libvips-integration.md`) или если в worker остаётся только пиксельный цикл без `canvas`. Плюс цена рестарта: загрузка lib, декодирование исходника — десятки или сотни мс на каждое прерывание.
- **Кооперативная отмена** — рендер-цикл в lib каждые N строк проверяет флаг «отменено» (`SharedArrayBuffer` + `Atomics`) и выходит. Worker живёт дальше, рестарта нет, `canvas` не мешает. Но придётся менять lib (сигнал отмены через `Layer` / `Composition`), а кодирование png внутри `canvas` так не прервать — только между фазами.

Делать, только если 2 секунды ожидания при перетаскивании реально мешают.

## Шаг 3 — координатор + рендер-узлы

Клиент шлёт всё подряд, без своей очереди. Рендер-узел обрабатывает всё, что ему приходит, тоже без очереди. Всё решение — что, куда и когда отправить — принимает координатор. Очередь не исчезает, а переезжает в одно место.

```
браузер ──ws──► координатор ──http──► рендер-узел(ы)
                (держит ws-соединения,  (POST граф → png,
                 последнее значение     без очередей,
                 на клиента, статус     один рендер за раз)
                 узлов, балансировка)
```

- **Websocket только между браузером и координатором.** С рендер-узлами — HTTP: рендер это ровно «запрос → ответ». Статус узла координатор знает и так: пока ждёт ответа, узел занят.
- **«Узел обрабатывает всё» — с оговоркой:** один рендер за раз на узел. Гарантирует координатор — не шлёт узлу больше, чем тот может взять.
- **Как шаг 1 переезжает в шаг 3.** Очередь (`ws.ts` + `render.ts`: кто свободен, последнее значение на клиента) уходит в координатор. Сам рендер в worker (`render-worker.ts`) уходит в рендер-сервис; внутри узла worker остаётся, чтобы HTTP-сервер узла не глох (health-check, запрос отмены).
- **Параллельность — процессами, а не потоками.** С `canvas` в процессе возможен только один рендерящий worker, поэтому несколько рендеров одновременно — это несколько процессов-узлов. Пул потоков внутри узла станет возможен только без `canvas`.
- **Прерывание в шаге 3** — запрос отмены от координатора к узлу или просто выброс устаревшего ответа. Через сеть сложнее, чем локально.
- **Название** — не «worker» (путается с Web Worker и worker threads), а gateway или dispatcher.
- **Граница в коде уже есть:** `ws.ts` вызывает `render(request)` из `render.ts`. В шаге 3 `render` становится HTTP-вызовом к узлу, а `ws.ts` — зародыш координатора.

Отдельный пакет под рендер-сервис нужен только здесь. Отдельный пакет под очередь не нужен ни на одном шаге: у неё один потребитель. Исполнитель графа может к тому времени уехать в lib как `Toast` — `docs/backlog/2026-10-06_render-boundary.md`. Нативный бэкенд (Zig + Skia, `docs/backlog/2026-10-06_native-backend-zig-skia-migration.md`) естественно становится реализацией рендер-узла за тем же HTTP-контрактом.

## Условие горизонтального масштабирования — общие загрузки

Сервер stateless, ws-соединение живёт на одном инстансе, поэтому N одинаковых серверов за балансировщиком можно поднять уже после шага 1. Мешает одно — загрузки на локальном диске (`assets/uploads/<imageId>`): картинка ушла на инстанс A, рендер пришёл на B → «image not found». Сначала s3 или общий volume (в спеке спринта 1 — «s3 for uploads — later»), потом несколько инстансов. Для шага 3 это тоже обязательно: рендер-узлы читают исходник из общего хранилища.

Для релиза 28.11 с пользовательскими тестами хватит одного процесса с шагом 1.
