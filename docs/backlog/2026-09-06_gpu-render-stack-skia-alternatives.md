# GPU-рендер-стек: альтернативы Skia после отказа от C++-шима

Skia отменяется как источник пиксельных примитивов (`blur`/`composite`/`affine-perspective`) для `packages/lib-native` — не из-за технической непригодности, а потому что в скачанном бинарном дропе (`rust-skia/skia-binaries`) нет `sk_capi`, и путь требует писать `shim.cpp`/`shim.h` на C++ в этом репозитории, что отклонено. `docs/specs/lib.spec.md` (раздел "Источник libskia") и пункты 4a-1/4a-2 в `docs/planning.md` описывают уже отменённый план — требуют ревизии на следующей сессии.

Ключевой реframe: libvips был отклонён в пользу Skia (`docs/backlog/2026-08-30_sharp-libvips-integration.md` → отменено `docs/backlog/2026-08-31_final-render-export-stack-architecture.md`) именно потому что Skia обещал "бесплатное" переключение CPU/GPU. Это обещание больше не бесплатное — GPU-путь Skia стоит ровно того C++-шима, от которого только что отказались. У libvips такой стоимости никогда не было: настоящий C API, готовые вызовы под каждую нужную операцию, без шима и без шейдеров. Так что сравнение больше не "GPU с ценой шима vs CPU без цены" — это "GPU с реальной ценой интеграции vs CPU почти без цены", на изображениях размером с мем-стикер (офлайн-батч, не realtime), где GPU-ускорение вряд ли даёт измеримый выигрыш.

Ресерч альтернатив (лёгких, GPU-желательных, атомарных — не whole-engine):

| Библиотека | API | GPU-бэкенды | Прекомпилированные Linux-бинарники | Лицензия | Поддержка | Трудозатраты под наш набор операций | Нужен новый shader/kernel код? |
|---|---|---|---|---|---|---|---|
| **libvips** | C | CPU-first (SIMD; часть операций через OpenCL) | Да, в дистрибутивах | LGPL-2.1+ | Очень активна | **Низкие** — `vips_boxblur`/`vips_composite2`/`vips_affine`/`vips_perspective` уже готовы | Нет |
| **wgpu-native** | C (`webgpu.h`) | Vulkan/GL/Metal/D3D12 | Да, ~16MB | Apache-2.0 | Активна (v29, июнь 2026) | Средние | Да — WGSL (текстовые строки, без build-time компилятора) |
| **sokol_gfx.h** | C, single-header | Metal/D3D11/GL compute | Header-only | zlib | Активна (compute добавлен 2025) | Средне-высокие | Да — кросс-компиляция через sokol-shdc |
| **Vulkan compute (vulkan-zig)** | C через Zig-биндинги | Только Vulkan | Нет (системный драйвер) | MIT | Полу-активна | Высокие | Да — GLSL→SPIR-V, нужен build-time компилятор |
| **libplacebo** | C | Vulkan/GL/D3D11 | Нет, сборка руками | LGPL-2.1+ | Активна | Высокие — фиксированный video-пайплайн, не покрывает произвольный warp/blend | Нет, но не подходит по функциям |
| **OpenCL** | C | Любой | Системный ICD | Khronos/драйвер | Стагнирует, не мертва | Средние | Да — OpenCL C kernels |
| **Zig `@Vector` SIMD, CPU** | Zig, без FFI | нет | — | — | — | **Низкие** (~150 строк/операция) | Нет — чистый Zig |

Ранжирование (открытый выбор, не решено):
1. **libvips** — ближе всего к принципу "готовое вместо самопального, 6 месяцев а не 6 лет" ([[xtc-toaster_build-vs-buy]]).
2. **wgpu-native** — если GPU всё же важен: чистый C, готовый бинарник, WGSL не требует тулчейна компиляции (в отличие от Vulkan/OpenCL), но остаётся boilerplate pipeline/bind-group ради 3-4 узких операций.
3. **Zig SIMD, только CPU** — самый "атомарный" (ноль зависимостей), но это ровно тот from-scratch путь, который уже был отклонён раньше по той же причине.

## Решение (2026-09-06, продолжение)

Выбран фазовый план, снимающий конфликт "доставка vs обучение GPU":

- **Фаза 1 — libvips, CPU.** Довести пиксельный низкий уровень (blur/composite/affine/perspective) до рабочего состояния через `vips_boxblur`/`vips_gaussblur`/`vips_composite2`/`vips_affine`/`vips_perspective` (готовые C-вызовы, точная сверка с текущим TS-кодом уже сделана в `docs/backlog/2026-08-30_sharp-libvips-integration.md`), протестировать, прокатать маршруты в реальном использовании. Никакого C++-шима не нужно — у vips уже родной C API, Zig зовёт его напрямую через `extern "C"`.
- **Фаза 2 — точечный GPU-переезд, отдельный трек.** Только после того, как маршрут на CPU уже прокатан и покрыт golden-value тестами — переписывать конкретный проверенный маршрут на GPU (кандидат — `wgpu-native`, чистый C API), попутно разбираясь с GPU-программированием с нуля. Явно **не** делается параллельно с первой доставкой — сначала работающий CPU-путь, потом (по желанию, без давления дедлайна тостера) отдельные маршруты переезжают на GPU по одному, с сохранённым CPU-путём как эталон для сравнения. Если после профилирования на реальных данных CPU окажется достаточно быстрым для размера картинок тостера — фаза 2 остаётся необязательной, а не невыполненным пунктом плана.

Это отменяет предыдущее решение (2026-08-31, та же таблица выше) держать одну C-либу (Skia) вместо libvips ради "бесплатного" CPU/GPU-переключения — то решение было основано на недооценке cтоимости GPU-пути (шим/биндинги), которая теперь явно вынесена в отдельную фазу вместо того, чтобы блокировать фазу 1.
