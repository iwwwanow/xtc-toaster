# Аудит тестов `packages/lib`: что покрыто, что нет, какие баги нашлись

Срез на 2026-10-03, master `3098ad5`. `bun test` — 58/58 зелёных, 10 файлов. Сами существующие тесты корректны (ассерты соответствуют коду), но покрывают в основном тривиальное. **Всё, что реально использует toast-1 (`perspective`, `blur`, `lch-hue`, `tint`), тестами не покрыто вообще.** Тесты нужны до любой оптимизации hot loops, потому что ускорение переписывает каждый цикл.

## Найденные баги (проверены пробами)

1. **`addHueNoise` — `preserveAlpha` ничего не делает.** Обе ветки дают одно значение (`a * 255` == `data[i+3]`). `preserveAlpha: false` → alpha 100 остаётся 100.
2. **Серые/белые/чёрные пиксели попадают в hue-маску 0°** (у них hue=0 по определению). `hueMask(серый, 0)` → alpha 255.
3. **`tolerance: 0` даёт пустую маску даже при точном совпадении** — деление 0/0 → NaN → 0.
4. **`rotate` крутит вокруг (0,0), а не центра** — `rotate(90)` выносит почти весь кадр за границы. Плюс forward mapping → дыры при любом повороте/scale>1 (известно, помечено в коде).
5. **`lch-hue` с серым FG перекрашивает фон**: hue серого не определён, `atan2(0,0)=0` → синий фон под серым FG становится `[0,102,0]`. Нужно: при нулевой хроме FG оставлять фон.
6. `boxBlur` не premultiplied — прозрачный чёрный подмешивается в цвет (красный|прозрачный → `[128,0,0,128]`, тёмный ореол). В toast-1 не проявляется, потому что `tint` идёт до `blur` и перекрашивает и прозрачные пиксели тоже, но ловушка для любого другого пайплайна.
7. Единицы в `MaskParams`: `value` — в градусах/процентах, `tolerance` — нормализованный 0–1. Не баг, но легко ошибиться из UI.

8. **`loopVideoTo` режет неточно**: `-c copy` режет только по границе пакета — цель 3 с даёт 3.33 с (20 кадров вместо 18). Для toast-1 это неполный цикл на шве петли.
9. **`speedUpVideo` x2 даёт не ту длину**: 3.33 с → 2.0 с вместо 1.67 с — ffmpeg держит исходный fps и дублирует кадры после `setpts`.

Каждый из 1–5, 8, 9 — решение о поведении, а не механический фикс; решает пользователь.

Гипотеза "8.3 с/кадр из-за `Matrix`" не подтвердилась — трансформы ~0.5–0.7 с. Общая причина медленности — аллокация массивов на каждый пиксель во всех сервисах (`readPixel`/`readNormalizedPixel`, `rgbToLab`/`rgbToHsl`/`hslToRgb` возвращают массивы, деструктуризация). Чинится одним проходом по всем hot loops, ≈2–3 ч.

| № | Решение |
|---|---|
