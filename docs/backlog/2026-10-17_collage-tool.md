# Инструмент для коллажей с поиском по индексированным базам

Идея на потом, не в рамках текущих спринтов. Инструмент собирается внутри xtc-toaster (как тост / набор нод), а не отдельным приложением. Поиск и индекс — общая часть с клипом из аудио: `docs/backlog/2026-10-17_audio-to-image-clip.md`.

## Части

**Поиск по базам.** Удобный поиск по двум источникам: личная база и открытые источники. Фильтры: по цвету, по тону, по объектам на изображении.

**Локальный индекс.** Открытые базы выкачиваются на локалку и индексируются. Первые параметры индекса: цвет, тон, объекты (распознавание того, что изображено). Набор параметров будет расти — индексатор должен уметь досчитывать новые параметры по уже скачанным изображениям. Запуск индексации — периодически (по расписанию) или ручным триггером.

**Слои.** Минимум функций: скрыть/показать, порядок (положение в стеке), группировка, имя. Больше ничего.

**Вырезание.** Лассо и волшебная палочка. Маски — опционально, если несложно в реализации (в lib уже есть `mask` по hue / saturation / value — возможно, волшебная палочка ложится рядом).

## Флоу

база (личная / открытая) → индексатор (цвет, тон, объекты, …) → поиск в GUI → изображение на канвас → вырезание → слои → экспорт коллажа.

## Понятия

- **база** — источник изображений: личная или открытая (скачанная локально);
- **индекс** — посчитанные параметры изображений, по которым идёт поиск; расширяемый;
- **индексатор** — процесс, который считает индекс; по расписанию или вручную.

## Уточнения (2026-10-17)

- **Источники нужны огромные.** Одних цветов (`~/Projects/datasets/102flowers`) мало: нужны большие открытые датасеты и стоки на сотни тысяч или миллионы изображений.
- **Превью + оригиналы.** При скачивании изображения подгоняются под рабочий размер где-то в диапазоне 64–512 px (точное значение подобрать на месте), чтобы интерфейс не тратил лишнюю память. Оригиналы сохраняются обязательно.
- **Идея: canvas-нода.** Коллаж собирается не отдельным приложением и не графом из нод-слоёв, а внутри одной ноды графа — `canvas-node`. Внутри неё строится свой интерфейс: toolbox (лассо, волшебная палочка), панель слоёв и т.д. Нода встраивается в граф как обычная: на вход изображения, на выход картинка. Её же можно использовать для раскладки кадров в клипе из аудио.

## Решение: поиск по эмбеддингам, теги — фильтры

**Понятия.**
- *Теги*: нейросеть-классификатор при индексации подписывает картинку словами из фиксированного словаря («собака», «море», «дом»), а поиск идёт по совпадению слов. Просто и прозрачно, но то, чего нет в словаре, не найдётся.
- *Эмбеддинг* — «отпечаток смысла»: картинка превращается в вектор из нескольких сотен чисел, и у похожих по смыслу картинок векторы близки. CLIP строит такие векторы для картинок и для текста в одном пространстве. Поэтому запрос «собака бежит по пляжу на закате» находит картинки без тегов, и так же работает «найди похожие на эту картинку».

**Решение.** Основной поиск — по эмбеддингам. Теги, цвет, тон и свои параметры хранятся в индексе как фильтры: найти «закат» по смыслу и отфильтровать по тону «тёмный». Всё считается одним индексатором за один проход.

Почему не теги как основа:
- слова из аудио непредсказуемы («тоска», «бежать», «ипотека»), а со словарём тегов на слове вне словаря поиск ничего не вернёт;
- для коллажа нужны свободные запросы («старая кирпичная стена в тумане»);
- поиск похожих по картинке возможен только на эмбеддингах;
- огромные скачанные базы не требуют разметки — вектор считается автоматически.

Теги остаются полезными: по ним видно, почему картинка нашлась, ими удобно точно фильтровать («только где есть люди»), а планируемые свои параметры по сути и есть ручные теги.

## Индексация эмбеддингов

Эмбеддинги считает нейросеть (image-энкодер CLIP), но видеокарта не обязательна: на картинки модель только применяется, а не обучается. Небольшие модели (CLIP ViT-B/32, MobileCLIP, маленькие SigLIP; 150–600 МБ) работают на CPU через ONNX Runtime.

Текущая машина: i5-11500 (6 ядер / 12 потоков), 30 ГБ RAM, встроенная Intel UHD 750 — для этого достаточно. Оценка без замера: порядка 10–30 картинок/с на CPU, то есть миллион картинок за половину суток — сутки. Это ложится на фоновый / ночной индексатор, который досчитывает только новое; число потоков ограничить, чтобы машина не подвисала.

Поиск дешёвый: текстовый запрос в вектор — миллисекунды; перебор миллиона векторов — ~2 ГБ в памяти и доли секунды.

Как не считать большие базы локально:
- **готовые эмбеддинги** — часть огромных открытых баз (например, LAION) поставляется с уже посчитанными CLIP-векторами; локально остаётся только текстовый энкодер той же модели для запросов;
- **арендованная GPU** — один раз прогнать большую базу за несколько часов, дальше досчитывать локально (`docs/backlog/2026-10-15_gpu-rental-for-custom-renderer.md`);
- **API эмбеддингов** — дороже на миллионах картинок и требует отдавать наружу личную базу.

**Первый шаг** — замер: прогнать маленькую CLIP на ~1000 картинок из `~/Projects/datasets/102flowers` (около получаса работы) и по скорости решить, хватает ли локальной индексации.
