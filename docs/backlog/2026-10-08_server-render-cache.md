# Кэш рендера на сервере; общую память клиент–сервер и разницу по кадрам не делаем

**Идея — кэш.** Держать в памяти сервера декодированный исходник по `imageId` и результаты нод по ключу «префикс цепочки + параметры». Тогда при движении слайдера в последней ноде пересчитывается только хвост цепочки. Это именно кэш, а не состояние: его можно потерять в любой момент, сервер остаётся stateless, переподключение по-прежнему бесплатное. С одной нодой (signac) выигрыш около 20 мс на декоде из 0.6–1.9 с кадра — делать, когда цепочки станут длинными. Нюанс: noize использует `Math.random`, и закэшированный результат даёт одинаковую картинку при одинаковых параметрах. Для превью это скорее плюс, но поведение меняется — решить явно.

**Вывод — разницу по кадрам не делаем.** Рассматривали вариант держать одинаковые `Uint8ClampedArray` в памяти клиента и сервера и слать только разницу с прошлым кадром. Для наших фильтров это ничего не даёт: noize меняет каждый пиксель по-разному при каждом рендере, а остальные операции lib (hue, маски, трансформации) глобальные — поменял параметр, поменялась вся картинка. Разница выгодна только при локальных правках, а таких операций нет. Зато появляется общее состояние: его нужно версионировать, сбрасывать при обрыве связи и держать побайтно одинаковым. Последнее упирается ещё и в предумноженную альфу canvas — `docs/backlog/2026-10-08_premultiplied-alpha-precision-loss.md`.

Крайний вариант той же идеи — рендерить в браузере: у клиента уже есть исходник, а `lib/domain` — чистый TS без DOM, его можно запускать в Web Worker. Это противоречит курсу на серверный нативный бэкенд (`docs/backlog/2026-10-06_native-backend-zig-skia-migration.md`) и правилу «web never imports lib». Это архитектурное решение, не оптимизация — пока не рассматриваем.
